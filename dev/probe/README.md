# DZProbe - what the WoW Forever client allows

A throwaway addon that measures the real Forever client (1.60.1, Interface 16001) so the port and the mock client
(`dev/tools/wowmock`) are built on facts instead of guesses. It sends nothing other players can see: addon messages use
its own `DZProbe` prefix, and the `/roll` test runs only when you are not in a group.

## Use

1. `dev/probe/install.sh` (Linux, Battle.net under Wine; set `WOW_DIR` to the WoW folder). On Windows, copy
   `dev/probe/DZProbe` into `World of Warcraft\_forever_\Interface\AddOns\` after running `gen_apilist.py`.
2. Log in. Five seconds later it runs its one-shot checks and prints "static run done".
3. `/reload` once (this proves whether `LoadSavedVariablesFirst` works), then just play. It logs passively whenever
   you enter combat, a dungeon or raid boss fight, a battleground, or an addon restriction switches on or off.
   Hover a few items so the tooltip hooks get counted. Loot something.
4. `/reload` or log out to save, then `python3 dev/probe/read_probe.py`. It writes
   `_DisasterZoneForever-vault/09-Reference/Forever Client Facts.md` and a JSON copy in `dev/probe/results/`
   (the dumps are not kept in the repo).
5. Remove it when done: `dev/probe/install.sh --remove`.
6. Feed the run into the tests (see `_DisasterZoneForever-vault/06-Operations/Testing with Forever Data.md`):
   `python3 dev/probe/mock_facts.py` refreshes the mock's Forever profile; `python3 dev/probe/export_replay.py RUN.json
   dev/tests/forever/fixtures/NAME.json --name "..."` turns a session worth replaying into a test fixture.

Commands: `/dzprobe` (summary), `/dzprobe run` (redo the static checks), `/dzprobe sample` (sample now), `/dzprobe reset`.

## What it answers

Build, `WOW_PROJECT_ID`, max level; `loadstring` / `setfenv` (in-game updates); `LoadSavedVariablesFirst` and TOC `X-`
fields; the loot methods (is master loot there?) and raid constants; `GetGuildRosterInfo`, rank index, officer notes
(their length only, never the text); which tooltip hook fires; whether the combat log can be registered; a 40-message
addon burst; the `/roll` line; item-cache behaviour; talents API; and which of the ~570 APIs and events the
DisasterZone addon uses are missing. The passive part builds a table of context (instance | combat | encounter |
active restrictions) against: can we send addon messages, is chat locked down, which unit/aura/cast/threat values are
secret. Secret values are never stored, only flagged.

## Round 2: group and raid (version 2)

Same addon, more checks, for a session with friends. Install it (`dev/probe/install.sh`), then in the group:

1. Form a party, then convert to a raid. Set **Master Looter** (you as looter) in the raid frame or with the right-click
   menu on your portrait.
2. Kill something with loot, open the corpse, and hand an item to someone from the master loot list.
3. Switch back to **Group Loot** and roll Need/Greed on something.
4. If you can, enter a raid or dungeon instance as a raid, and do a battleground.
5. `/reload` or log out, then `python3 dev/probe/read_probe.py`.

It records how readable the raid roster is (per field: readable or secret, never the names), the loot method
changes, master-loot candidates (counts only), roll items, and its own name forms. Other members' names are never
stored; the guild roster is reduced to name shapes (space / hyphen counts). Round 2 writes
`09-Reference/Forever Client Facts - Round 2.md`, leaving round 1 untouched.
