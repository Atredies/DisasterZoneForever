# Probe Findings 2026-11-08

What the first full DZProbe run (a level-17 character, ~4 h incl. a full Deadmines clear with 9 boss pulls) means for
the port. Raw numbers: [[Forever Client Facts]] (regenerated by `dev/probe/read_probe.py`); the run dumps are not kept
in the repo.

## Good news

- **Hotpatch can work as upstream does:** `loadstring` and `setfenv` run, `LoadSavedVariablesFirst` is honoured
  (the one `false` was the very first load, before any SavedVariables existed).
- **Master loot is there:** `Enum.LootMethod.Masterlooter`, `C_PartyInfo.SetLootMethod`, `GiveMasterLoot`, loot
  style `Vanilla`. Loot council hand-out is possible (still to test in a real raid group).
- **40-player raids:** `MAX_RAID_MEMBERS` 40, 8 groups of 5.
- **Guild roles work:** roster rows readable, rank index 0 = Guild Master, rank names readable, officer notes
  viewable and editable.
- **All 77 `C_` functions DZ uses exist.**
- **Encounter events are not secret:** `ENCOUNTER_START`/`END` give readable name, id, difficulty, size.
- **Loot links are readable** in instances; `/roll` lines parse with `RANDOM_ROLL_RESULT`; `START_LOOT_ROLL` fires.
- **Tooltips:** only `TooltipDataProcessor` (fired ~30k times); `OnTooltipSetItem` is gone.

## The big constraint: no addon messages during a boss pull

From `ENCOUNTER_START` to `ENCOUNTER_END` the client switches on the **Encounter + Chat** restrictions and every
`SendAddonMessage` (PARTY, GUILD, WHISPER) returns `AddOnMessageLockdown`. Both lift in the same second as
`ENCOUNTER_END`, kill or wipe. Ordinary combat and being inside an instance (the `Map` restriction) do not block
sends.

**For the port:** `Comm` must queue outgoing messages while `C_ChatInfo.InChatMessagingLockdown()` is true and flush
on `ENCOUNTER_END` / `ADDON_RESTRICTION_STATE_CHANGED(Chat, Inactive)`. Loot council, attendance and sign-ups happen
between pulls, so they are unaffected once the queue exists.

## Secret values

- `UnitHealth`, `UnitHealthMax`, `UnitPower` are secret **everywhere**, even out of combat in the open world.
- Inside an instance `UnitName(target)` and `UnitGUID(target)` are secret too; `UnitCastingInfo(target)` mostly.
- Not yet measured: whether `GetRaidRosterInfo` / `UnitName("raidN")` are secret in a raid instance. That decides
  how the session crest and attendance read the roster in a raid. Needs a raid group.

## Combat log

Registering `COMBAT_LOG_EVENT_UNFILTERED` triggers ADDON_ACTION_FORBIDDEN and the "Blizzard UI only" popup. No addon
combat log at all. Combat features must use `C_DamageMeter`, `C_EncounterTimeline`, `C_SwingTimer` (all present).

## Throttle

40 addon messages in a burst on GUILD: 9 sent, 31 `AddonMessageThrottle`. ChatThrottleLib pacing stays essential.

## Names have spaces (confirmed 2026-11-08, fixed)

Forever has **regionally unique names**: a character is a first name plus a surname, "Name Surname". Measured in game:
`UnitName("player")` and `UnitFullName("player")` give `"Name"` (second return: the surname `"Surname"`, where other
clients return the realm), `GetUnitName("player", true)` gives `"Name Surname"`, and the guild roster row is
`"Name Surname"` with no realm. Blizzard's Forever UI confirms it (`Blizzard_FrameXMLUtil/Camelot/NameUtil.lua`,
`RegionalUniqueNamesEnabled()`).

DisasterZone keyed itself from `UnitName` ("Name") while the roster, chat and addon-message senders said
"Name Surname": the GM was not the GM to their own addon and their own messages came back as another player's.
Fixed with `Util.UnitNameRealm` (see [[Decision Log]]), confirmed in game: `RegionalUniqueNamesEnabled()` true,
the second value of `UnitName` / `UnitNameUnmodified` / `UnitFullName` is the surname, and `GetUnitName(unit, false)`
also returns "Name Surname". Still unmeasured: the name `GetRaidRosterInfo` returns in a
raid (probe round 2).
